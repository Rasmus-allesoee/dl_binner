# Human-Microbiome Data and CPU-Only Execution Audit

Date: 2026-09-18. Scope: targeted primary-source checks, public directory/checksum metadata, tiny HTTP range reads, and the already pinned native code. No complete research dataset, mapper benchmark, binner fit or scientific score was produced. Decision: [D004](../decisions/D004-human-cpu-preflight.md).

## Dataset reassessment

The owner's human-health priority is decisive: Marine was chosen for a released ten-sample known-origin diagnostic, not because marine biology was needed. The HMP gastrointestinal subset supplies the relevant public human-associated starting point. CAMI III toy human gut is a serious later option, but starting with its larger longitudinal collection adds no necessary control for the present fixed-assembly thinning question. Real clinical metagenomes are valuable validation data but lack the contig-origin truth needed here. New CAMISIM communities remain useful when an identified mechanism requires control unavailable in public data.

**Source report:** [CAMI's HMP page](https://cami-challenge.org/datasets/toy-human-microbiome-project/) describes 49 samples across five human body sites, including ten GI samples, with short reads of 2 x 150 bp and RefSeq source genomes dated 2017-08-07. This is a simulation informed by HMP profiles, not patient-level clinical evidence. Old public source genomes imply substantial potential reference/pretraining overlap: this cannot serve as a final unseen-genome test.

**Direct metadata observation:** the [archive README](https://frl.publisso.de/data/frl%3A6425518/README.md) explicitly assigns GI samples `0,1,2,3,4,5,9,10,11,12` within `gastrooral/`. The other ten samples are oral. It directs users to body-site-specific gold standards. Therefore the shared setup's pooled assembly must not be assumed GI-specific. The [GI directory](https://frl.publisso.de/data/frl%3A6425518/per_bodysite/gastro_bam/) lists `gsa.fa` (~927 MB displayed), `gsa_pooled_mapping_fixed.tsv` (~12 MB), and the original mapping (~24 MB), alongside source-genome BAMs and per-genome FASTAs. [Gastrooral archive metadata](https://frl.publisso.de/data/frl%3A6425518/gastrooral/) lists a ~1.8 GB setup and roughly 9-10 GB per sample archive. These are rounded listing sizes, not measured storage requirements.

**Direct bounded prefix observation:** 1 KB of `gsa.fa` begins with `CP013019.1_from_3_to_4351861_total_4351859`. A 4 KB prefix of the fixed mapping has `#anonymous_contig_id, genome_id, tax_id, contig_id, number_reads, start_position, end_position` as tab-separated columns; `PC0` points to that accession and inclusive interval. The 2 KB original-mapping prefix contains conflicting associations for subsequent anonymous IDs. This establishes a need for strict coordinate/length joins and the fixed table, not correctness of the entire corrected file. Source-coordinate FASTA names will be replaced with the corresponding anonymous IDs before any binner sees them. Sequence content stays unchanged; the original-to-anonymous map is preserved.

The [publisher MD5 manifest](https://frl.publisso.de/data/frl%3A6425518/md5sums.tsv) supplied the literal checksums in [acquisition.json](../../experiments/E001-coverage-thinning/acquisition.json). No payload checksum has been verified locally. A publisher hash establishes file identity, not biological correctness. Full joins, duplicate detection, taxonomy, sample layout, short-contig support and the fixed genome population remain owner-run inventory gates. The official historical-taxonomy link is recorded as a candidate, not a verified available payload.

## Mapper alternatives

These are source reports and selection reasoning, **not reproduced speed ratios**. Runtime, memory and mapping ambiguity depend on reference size/redundancy, read characteristics, version, settings and hardware. Human-genome mapping figures do not establish metagenomic binning performance.

| Mapper | Relevant evidence and implication |
| --- | --- |
| BWA-MEM2 | The [official README](https://github.com/bwa-mem2/bwa-mem2) reports a reduced human-genome index footprint of about 10 GB following a 2020 change, rather than the older ~40 GB memory figure. It was a reasonable conventional choice, not uniquely required by E001. Index construction and total peak memory still need separate measurement. Do not repeat old RAM numbers as current universal requirements. |
| Bowtie2 | The [official manual](https://raw.githubusercontent.com/BenLangmead/bowtie2/master/MANUAL.markdown) describes a compact FM index and approximately 3.2 GB memory for a human-genome example. It supports end-to-end and local alignment, with different defaults. Its mature tooling and the owner's familiarity make it the preferred comparison/fallback, not grounds to assume identical coverage. |
| strobealign | The [v0.17.0 README](https://raw.githubusercontent.com/ksahlin/strobealign/v0.17.0/README.md) supports paired/interleaved 150 bp reads and full SAM alignment. We choose this released C++ version for the CPU-first preflight, not mutable Rust `main`. Its separate `--aemb` abundance mode fractionally weights multimappers and lacks the alignments/variance needed by E001; do not use it here. [Release history](https://github.com/ksahlin/strobealign/releases) documents algorithm changes, so older headline speedups are not measurements of this pin. |
| minibwa | The [author README](https://github.com/lh3/minibwa) reports faster short-read alignment than BWA-MEM/BWA-MEM2 using a different algorithm. Its BWA-compatible CLI does not imply identical alignments; indexing uses roughly 18 times reference length in RAM by default, with a lower-memory option. [Releases](https://github.com/lh3/minibwa/releases) already exist, so dismissing it as unreleased would be wrong. It is a legitimate alternative, but adding a fourth mapper now does not improve the immediate binner diagnostic. |

**Decision reasoning:** use strobealign 0.17.0 full SAM, preserving the existing primary-alignment flag contract, provisionally. First verify SAM flags, mate handling, NM tags and downstream feature compatibility on synthetic data. Then assess one fixed real-read prefix against Bowtie2 before committing mapping spend. Different alignments are not automatically errors; inspect ambiguity and downstream coverage, and freeze any change before binner scores. Do not select a mapper by maximizing the diagnostic's recovery gap.

## CPU feasibility and native code

The owner now reports **no GPU**, 1-128 AMD EPYC 9535 vCPU, 3-384 GB RAM, approximately 2,100 allocated core-hours and 250 GB storage; more storage may be obtainable. This supersedes older H200/large-memory assumptions, not merely the initial job request. GB is retained as reported; it is not relabeled GiB.

At the [pinned commits](2026-09-17-tool-snapshots.json), `COMEBin/COMEBin/train_CLmodel.py::_resolve_training_device` explicitly accepts CPU and `run_comebin.sh -d cpu` propagates it. The native model has wide networks, six views and pairwise contrastive comparisons, so CPU support does not prove affordability. `vamb/vamb/encode.py::VAE` defaults to CPU; its command-line GPU option is opt-in. Neither method needs a new implementation to attempt CPU execution. Environment and throughput validation remain unexecuted locally.

Keep the three intended baselines pending measured feasibility. A COMEBin budget failure cannot satisfy the COMEBin-specific triage rule or be disguised as a negative biological result. If it is too expensive, explicitly amend to a narrower MetaBAT2/VAMB diagnostic (with new decision criteria) or defer the learned comparison, before seeing scientific results. This is preferable to silently reducing native epochs/width or spending the entire project allocation on the first diagnostic.

The [configuration](../../experiments/E001-coverage-thinning/config.json) sets nested stop/review limits and a reserve; [operations](../../experiments/E001-coverage-thinning/OPERATIONS.md) explains charged core-hours, sequential storage and gates. These are planning decisions, not measured requirements. Tiny forward passes establish compatibility only. Full-batch CPU timing, marker/clustering checks and one-library storage expansion are still needed before scientific launch.
